## The toolbar, control by control

**Record** (the red dot) is on by default. **Clear** (⊘) empties the list — press it immediately before the action you want to study, so the list contains only that action.

**Preserve log.** Keeps requests across navigation. Turn it on before any flow that redirects: login, checkout, OAuth. Without it the request that caused the redirect vanishes.

**Disable cache.** While DevTools is open, everything is fetched fresh. Leave this on permanently.

**Throttling.** Simulate a slow connection. Choose *Slow 4G* and retest a flow — you will find race conditions, missing loading states and double-submits that never appear on a fast office connection. This is one of the highest-value, least-used features in DevTools.

**Offline.** Check what happens when the connection drops mid-flow. Most applications handle this badly, and it is a legitimate finding.

## Filters

The row beneath: **All, Fetch/XHR, Doc, CSS, JS, Font, Img, Media, Manifest, WS, Wasm, Other.**

**Fetch/XHR is the one you want**, nearly always. It hides images, fonts and stylesheets and shows only the application's data calls.

The text box filters by URL, and it takes more than plain text:

- `status-code:500` — only server errors.
- `method:POST` — only POSTs.
- `larger-than:1M` — only big responses.
- `-.png` — a leading minus excludes.
- **Invert** flips the whole filter.

<Callout kind="job">
`status-code:500` typed into that box is the fastest triage move in existence. On a page misbehaving in some vague way, it answers "is anything actually failing?" in one second, and if something is, you have the exact endpoint.
</Callout>

## The columns

Right-click the header row to add columns. Three worth adding permanently:

- **Method** — so you can see GET versus POST without clicking.
- **Type** — xhr, fetch, document, script.
- **Priority** — how the browser ranked it.

**Status** is the one your eye should go to first. **Time** finds the slow one. **Size** shows whether something came `(from disk cache)` or over the wire — which matters when a fix seems not to have taken effect.

## Inside one request

Click any request for its tabs. You know these from week 1; here is what each is actually best for.

**Headers** — the URL, method, status, and both sets of headers. Where you find the request id to quote in an escalation.

**Payload** — what you sent. This is where you catch a wrong amount, a missing field, or a form value that never left the browser because the input had no `name`.

**Preview** — the response as an expandable tree. Easier for finding a value.

**Response** — the raw body. Use this one for reading error messages exactly, and for spotting things that should not be there at all.

**Initiator** — what caused the request. Use it to trace a mystery call, or a duplicate.

**Timing** — where the time went. **Waiting for server response** is the number that matters: high means the server is slow, low with a high total means the network or the payload size is the problem.

<Callout kind="key">
The Response tab is where security findings live. You are reading it for **things that should not be there**: password fields, full card numbers, other customers' records, internal flags, stack traces.

The screen will not show you any of this. The response will. In week 14 this becomes one of the five security checks; for now, build the habit of actually reading the raw response rather than glancing at Preview.
</Callout>

## Copy as cURL, and HAR files

**Right-click a request → Copy → Copy as cURL** gives you the complete command to reproduce that exact request from a terminal or Postman. This is how you hand a developer something they can run, and how you take a request out of the browser to experiment with — week 8.

**Right-click → Save all as HAR** exports the whole session.

<Callout kind="watch">
Both of these contain **everything**: your `Authorization` header, cookies, session tokens, and any personal data in the bodies.

A cURL command pasted into a ticket is a live credential pasted into a ticket. A HAR attached to a public tracker is a full session handed to anyone reading it.

Redact before sharing, every time. Replace the token with `REDACTED`. If you cannot sanitise a HAR properly, do not attach it — describe the requests instead.
</Callout>

## Reading a waterfall

The bars on the right show when each request started and how long it took.

- **Long bars** — slow individually.
- **Staircases** — requests waiting on each other. Often a chain that could have run in parallel.
- **A gap before everything** — the page was busy doing something else first.
- **Many tiny bars** — lots of small requests, which can be slower than one big one.

You do not need to optimise anything. You need to describe it: "the dashboard makes 34 requests and the last finishes 4.2 seconds after load; `/api/summary` alone waits 2.8 seconds for the server."
