Three smaller topics that together close out DevTools: where the browser keeps things, whether the connection is sound, and how to test at other sizes.

## Application: where state lives

<Video id="devtools-storage" />

The Application panel shows everything the site has stored in your browser. Four places matter.

**Cookies.** Small values sent automatically with every request to that domain. Usually where a session lives. Each has flags worth reading:

- **HttpOnly** — JavaScript cannot read it. A session cookie without this can be stolen by any script on the page, which is a real security finding.
- **Secure** — only sent over HTTPS. Missing is a finding.
- **SameSite** — controls whether it is sent on cross-site requests.
- **Expires** — when it dies. A session cookie with a one-year expiry is worth questioning.

**Local Storage.** Key-value pairs that persist until cleared. Often holds a login token, user preferences, a cached basket. **Readable by any JavaScript on the page**, so a token here is less safe than one in an HttpOnly cookie.

**Session Storage.** The same, but cleared when the tab closes.

**IndexedDB.** A larger database for offline data. You will rarely need it.

<Callout kind="watch">
Look at what is actually stored. Finding a password, a full card number, a national identity number or another customer's details in Local Storage is a serious, reportable finding — and it happens more often than you would expect, because developers reach for it as a convenient place to park things.

Report it as a security issue, and redact the value in your evidence. You are proving the field exists, not republishing it.
</Callout>

## Clear site data

Bottom of the Application panel's Storage section: **Clear site data**.

It wipes cookies, storage and caches for that origin, giving you a genuinely fresh browser without a new profile or an incognito window.

This matters more than it sounds. A huge proportion of "I cannot reproduce it" comes from the tester being logged in, having a populated basket, or holding a cached file the real user does not have. **First-visit behaviour is a different test from returning-visit behaviour**, and most bugs in onboarding, consent banners and empty states only appear on a true first visit.

<Callout kind="job">
Build the habit: before testing any first-run experience — signup, onboarding, an empty dashboard, a cookie banner — clear site data first. Otherwise you are testing the returning-user path and calling it the new-user path.
</Callout>

## Security

Click the Security panel and reload. It tells you whether the connection is sound and the certificate valid.

For anything handling money or personal data, confirm:

- The connection is HTTPS with a valid, in-date certificate.
- There is no **mixed content** — HTTP resources on an HTTPS page. The browser may block them silently, so a page can be subtly broken with no visible error.

A padlock in the address bar covers most of this, but the Security panel tells you *why* when something is wrong.

## The device toolbar, properly

You used this in week 3. Three things worth adding.

**The preset list** covers common phones and tablets. The dropdown also offers **Responsive**, which lets you drag to any width — better for finding breakpoints.

**Throttling is here too**, combined with the size. A phone preset plus Slow 4G is much closer to a real user in Lagos on a patchy connection than a desktop on office wifi.

**The three-dot menu** adds:
- **Show device frame** — a phone outline, which is nicer for screenshots in reports.
- **Capture screenshot** — the emulated viewport only.
- **Show rulers** — pixel measurement, useful for checking tap target sizes.

<Callout kind="watch">
Emulation changes the viewport and the user-agent string. It does **not** reproduce real touch behaviour, the on-screen keyboard, device performance, or OS-level quirks.

Reload after switching sizes, too — anything that ran at load time, like a device check, will not re-run on resize, so you can get a misleading result.
</Callout>

## Lighthouse, briefly

The Lighthouse panel runs an automated audit and scores performance, accessibility, best practices and SEO.

It is a useful baseline and a poor substitute for thinking. It catches missing alt text and contrast failures; it cannot tell you the tab order is nonsense, or that the error message is misleading, or that the checkout charges twice. **A perfect Lighthouse score on an unusable page is entirely possible.**

Run it for a starting point. Never report its score as a conclusion.
