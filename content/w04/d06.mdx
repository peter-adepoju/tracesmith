## The hunt

**Elements**

1. How many `<button>` elements are on the catalogue page?
2. Find an element that is in the DOM but not visible on screen. What is hiding it, and which of the three methods is it?
3. Pick any price. What is its computed `color`, as a hex or rgb value?
4. Force the `:hover` state on a View button. What changes?

**Console**

5. Are there any errors on load? If so, which file produced each one, and is it the site's own code or a third party?
6. How many images on the page are missing an `alt` attribute?
7. Print the heading outline. Does it have exactly one `h1` and no skipped levels?

**Network**

8. How many requests does the page make on first load? How many are Fetch/XHR?
9. Find the request that fetches the products. What is its status, and how long did it wait for the server?
10. Add something to the cart. Which request fires, and what exactly is in its payload?

**Application and device**

11. Does the site store anything in Local Storage or cookies? If so, what?
12. At 375 pixels wide, does the page scroll horizontally? If it does, which element is the culprit?

## Scoring yourself

- **Under 10 minutes** — you are fluent. Move on.
- **10 to 20 minutes** — normal after one week. Repeat it in a few days.
- **Over 20 minutes** — note which questions cost you the time and reread that day. There is no shame in it; this is a lot of surface area for one week.

The questions you found hardest tell you which panel to practise. That signal is the real output of today, more than the answers.

## Two habits to carry forward

**Open DevTools first.** Before you touch the page, not after something goes wrong. Console and Network only record while they are open, and there is nothing more irritating than reproducing a rare bug and having no evidence of it.

**Read the response, not the screen.** The screen shows what the page chose to display. The response shows what the server actually sent. Almost everything interesting — missing data, leaked data, the wrong value, the real error message — lives in the gap between the two.

## Phase 1 complete

Twenty-four days. Look at what you can now do.

You can follow a request from a URL to a response and back, name every step, and say whose problem a failure is from the status code alone. You can read HTML and say what it means rather than what it looks like, test a form systematically, and run an accessibility pass in five minutes. You can read CSS well enough to say which rule won and why, explain why an element is the wrong size, and tell a missing element from a hidden one. You understand the DOM as a live tree distinct from the file the server sent — and you use that distinction to assign a bug to the front end or the back end. And you can work every DevTools panel that matters.

That is the foundation all three careers stand on, and it is more than many working testers can do.
