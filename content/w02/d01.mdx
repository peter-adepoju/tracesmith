## HTML is structure, not appearance

This is the idea people get wrong, and getting it right early saves a lot of confusion.

HTML says **what something is**. CSS says **what it looks like**. JavaScript says **what it does**.

An `<h1>` is not "big bold text". It is "the main heading of this page". It happens to render large and bold by default, but that is a default, not its meaning. You can make an `<h1>` look like anything. What you cannot do is change the fact that screen readers announce it as the main heading, search engines weight it, and keyboard navigation uses it.

<Callout kind="key">
When you choose a tag, you are describing meaning. Choosing `<div>` for everything produces a page that looks right and is meaningless to anything that is not a pair of human eyes. In week 12 that becomes an accessibility finding you will know how to write.
</Callout>

## The smallest real page

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>Orders</title>
  </head>
  <body>
    <h1>Your orders</h1>
    <p>You have no orders yet.</p>
  </body>
</html>
```

Every line earns its place:

- **`<!doctype html>`** — tells the browser to use modern standards. Leave it out and the browser switches to "quirks mode", emulating a browser from 1998, and your layout breaks in ways that are very hard to diagnose. This is a real bug you may meet.
- **`<html lang="en">`** — the whole document, and what language it is in. Screen readers use `lang` to choose a pronunciation.
- **`<head>`** — information *about* the page. None of it is displayed.
- **`<meta charset="utf-8">`** — which character encoding. Get this wrong and accented characters and emoji turn into mojibake like `â€™`. Another real bug with a very specific cause.
- **`<meta name="viewport" ...>`** — tells a phone to use its real width instead of pretending to be a desktop. Missing viewport tag is the single most common cause of "the site is tiny and zoomed out on mobile".
- **`<title>`** — the browser tab, and the heading in search results.
- **`<body>`** — everything a person actually sees.

<Callout kind="job">
Three bugs are already in reach: quirks mode from a missing doctype, mojibake from a wrong charset, and a broken mobile layout from a missing viewport tag. Each has an obvious symptom and a one-line cause. Testers who know them diagnose in seconds what others spend an afternoon on.
</Callout>

## What the browser does with a tag it does not know

Try this thought experiment: what happens if you write `<banana>hello</banana>`?

Nothing dramatic. The browser does not error. It does not refuse the page. It creates an element it has no styling or behaviour for, and displays the text inside it.

HTML is deliberately forgiving. It will render a broken page rather than show nothing, because a half-readable page is better than a blank one for a reader.

That forgiveness is a double-edged thing for you:

- **Good**: one typo does not take a site down.
- **Bad**: mistakes are silent. A misspelled tag, a missing closing tag or a mistyped attribute produces no error message at all, just subtly wrong output.

<Callout kind="watch">
This is why "it looks fine" is not a test result. HTML has no compiler to tell you it is wrong. The browser's Elements panel, which you meet in week 4, shows you what the browser actually built — which can differ from what you wrote.
</Callout>

## Write one yourself

You do not need an editor or an account. You need Notepad or TextEdit.

<Callout kind="practice">
1. Open a plain text editor.
2. Type the page above, by hand. Do not copy and paste: typing it is the point.
3. Save it as `test.html` — making sure your editor does not append `.txt`.
4. Double-click the file. It opens in your browser.
5. Change the `<title>`, save, and refresh.

You have now served yourself a page. No server, no internet. The browser read a file and built a document from it.
</Callout>
