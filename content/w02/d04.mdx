## What a form actually is

```html
<form action="/orders" method="post">
  <label for="email">Email</label>
  <input type="email" id="email" name="email" required />

  <button type="submit">Place order</button>
</form>
```

A form is a container that collects values and sends them somewhere.

- **`action`** — the URL the values go to.
- **`method`** — `get` or `post`. You know what those mean from week 1.
- **`name`** — the key each value is sent under. **An input with no `name` is not submitted at all.** It will look perfectly normal on screen and its value will silently never arrive.

<Callout kind="watch">
A missing `name` attribute is one of the sneakiest bugs in web development. The field renders, accepts typing, passes visual inspection, and vanishes on submit. You find it in the Network tab's Payload, not on the screen — which is exactly why week 1 came first.
</Callout>

## Labels, and why they are not decoration

```html
<label for="email">Email</label>
<input type="email" id="email" name="email" />
```

The `for` attribute must match the input's `id`. When it does, three things happen:

1. A screen reader announces "Email" when the field gets focus.
2. Clicking the label focuses the input — a noticeably larger tap target on a phone.
3. Automated tests can find the field by its visible label instead of a brittle CSS path.

A field with a visual label that is not a real `<label>`, or whose `for` does not match, is a genuine accessibility finding. Checking it takes seconds: click the label text. If focus does not move to the field, it is not wired up.

## Input types

The `type` attribute changes behaviour, validation and the keyboard a phone shows.

| Type | What it gives you |
| --- | --- |
| `text` | Anything |
| `email` | Basic format check, email keyboard on mobile |
| `password` | Characters masked |
| `number` | Numeric keyboard, `min`, `max`, `step` |
| `tel` | Phone keypad on mobile, no validation |
| `date` | A date picker |
| `checkbox` | On or off, independently |
| `radio` | One of a group, sharing one `name` |
| `file` | A file picker, with `accept` |
| `hidden` | Sent but not shown |

<Callout kind="key">
Three things worth remembering from that table.

**`type="number"` still accepts pasted text** in several browsers, and `min` is trivially bypassed by typing. Never trust it.

**Radios are grouped by `name`, not by position.** Two radio groups accidentally sharing a `name` means selecting one clears the other — a real and very confusing bug.

**`type="hidden"` is not secret.** It is visible in the Elements panel and editable by anyone. A price in a hidden field is a serious defect, and one worth looking for.
</Callout>

## Client validation is a convenience, never a control

```html
<input type="email" name="email" required minlength="3" maxlength="64" />
```

These attributes make the browser refuse to submit. That is good for users and worth nothing for security.

Anyone can bypass every one of them: edit the attribute in the Elements panel, disable JavaScript, or skip the page entirely and send the request directly with Postman — which you will do in week 8.

<Callout kind="job">
**The server must validate everything the client validates.** Testing only through the form tests only the polite path.

The real test is: strip the constraint in DevTools, submit, and see whether the server catches it. If a form refuses a 500-character name but the API accepts one happily, you have found a real defect that no amount of clicking would reveal. This is one of the highest-value things a tester can do, and most do not do it.
</Callout>

## Select, textarea, and the rest

```html
<select name="country">
  <option value="">Choose…</option>
  <option value="NG">Nigeria</option>
  <option value="GH">Ghana</option>
</select>

<textarea name="notes" rows="4"></textarea>
```

Watch the gap between an option's **value** and its **label**. `<option value="A">Section A</option>` submits `A`, not `Section A`. When those two drift apart, a form can silently save something other than what the user picked — a defect that is invisible on screen and obvious in the Payload tab.

## How to break a form, systematically

Do not poke at random. Work the list.

1. **Empty** — submit everything blank. Are required fields enforced, on the server as well?
2. **Boundaries** — the shortest and longest allowed value, then one past each.
3. **Wrong type** — letters in a number field, `notanemail` in an email field.
4. **Negative and zero** — in any numeric field, especially quantities and amounts.
5. **Whitespace** — a single space. Is it trimmed, or accepted as a name?
6. **Special characters** — apostrophes in names, accents, emoji. `O'Brien` breaks more systems than you would believe.
7. **Very long input** — paste 10,000 characters. Does it truncate, reject, or fall over?
8. **Double submit** — click the button twice, fast. You met this in the Meridian lab.
9. **Back and resubmit** — submit, press back, submit again.
10. **Bypass the client** — remove `required` in DevTools and submit anyway.

<Callout kind="practice">
Pick any signup form on a site you do not mind poking, and work items 1 to 7 of that list. Keep the Network tab open and read the Payload for each attempt.

Write one finding per real problem, in the format from week 1 day 6: what you did, what came back, what it means.
</Callout>
