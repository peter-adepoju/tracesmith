One saved request is a note to yourself. A collection with environments is a tool other people can use — and the thing that stops you firing a test at production.

## Collections

A collection is a named folder of requests. Make one per API, with folders inside per resource:

```
Meridian API
├── Customers
│   ├── List customers
│   ├── Get one customer
│   └── Create a customer
├── Payments
│   ├── Initiate
│   └── Verify
└── Health
    └── Ping
```

Name requests by **what they do**, not by method and path. "List customers" beats "GET /v1/customers" — you can see the method on the row already, and a human-readable name is what makes a collection browsable by someone who has never seen the API.

## Variables

Hard-coded values are what make a collection disposable. Variables are what make it last.

```
{{baseUrl}}/v1/customers/{{customerId}}
```

Four scopes, and you mostly need two:

| Scope | Lives | Use for |
| --- | --- | --- |
| **Environment** | Per environment | `baseUrl`, keys, test accounts |
| **Collection** | With the collection | Things identical everywhere |
| Global | Across everything | Avoid. Hard to trace |
| Local | One run | Set by a script, covered on day 4 |

## Environments, which are the point

An environment is a named set of variables you switch between.

**Sandbox**
```
baseUrl    https://api-sandbox.example.com
apiKey     sk_test_trace_93ba07
```

**Production**
```
baseUrl    https://api.example.com
apiKey     sk_live_••••••••
```

Same collection, one dropdown. Every request follows.

<Callout kind="key">
This is the feature that stops the worst mistake available to you.

With a hard-coded URL, testing against production means editing a request — and forgetting to change it back. With environments, the current one is **named in the corner of the window at all times**, and switching is deliberate.

Make a habit of reading that dropdown before any request that changes something. Out loud, if you are near production.
</Callout>

## Secrets in Postman

Mark any variable holding a key as **secret** in the environment editor. Postman then masks it in the interface and leaves it out of exports.

Which matters, because:

<Callout kind="watch">
**Exporting a collection or environment exports the variable values.** Share that JSON in a ticket or commit it to a repository and you have shared your keys.

Mark secrets as secret. Before sharing an export, open it and look. It is a plain JSON file, and reading it takes ten seconds.
</Callout>

## Documentation for free

Each request has a **Description** field, and Postman turns a collection into a documentation page from them.

Two sentences per request — what it does, what it needs — produces something genuinely useful. When a merchant asks "how do I call this?", a link beats a paragraph, and you wrote it as a side effect of organising your own work.

## Build one

Make a collection for any public API. [api.github.com](https://api.github.com) works and needs no key.

1. A collection called **GitHub**.
2. An environment **Public**, with `baseUrl` set to `https://api.github.com`.
3. Three requests using `{{baseUrl}}`: get a repository, list its issues, get a user.
4. A `{{owner}}` and `{{repo}}` variable so the first two work for any repository.
5. A one-line description on each.

Then change `{{repo}}` once and watch every request follow. That is the moment collections make sense.
