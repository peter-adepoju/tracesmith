Real flows are several requests in order, where each one needs something the last one produced. Log in, get a token, use the token. Create an order, get its id, pay for it.

Today you stop copying values between requests by hand.

## Why order matters

```
1. POST /auth/login          → { "token": "eyJ..." }
2. POST /v1/orders           → { "id": "ORDER-1001" }    (needs the token)
3. POST /v1/payments/initiate → { "checkout_url": "…" }  (needs the token and the id)
4. GET  /v1/payments/verify/ORDER-1001                   (needs both again)
```

Each step depends on the one before. Run them out of order and you get a 401 or a 404 that tells you nothing about the actual system.

<Callout kind="key">
**A dependency failure looks exactly like a real bug.** A 404 on step 4 might mean verification is broken, or might mean step 2 never ran and there is simply no such order.

So before reporting any failure in a sequence, confirm the earlier steps actually succeeded. "Step 4 returns 404" is not a finding until you can say step 2 returned 201 with that id.
</Callout>

## Capturing a value

In Postman, the **Scripts → Post-response** tab runs after a response arrives. Three lines do the job:

```js
const body = pm.response.json();
pm.environment.set("token", body.token);
```

Now `{{token}}` is available to every later request. Set it once in the login request and the whole collection follows.

For the order:

```js
const body = pm.response.json();
pm.environment.set("orderId", body.id);
```

And the next request uses `{{baseUrl}}/v1/payments/verify/{{orderId}}`.

That is genuinely all the scripting most testers ever need: read the response, save a value.

## Checking as well as capturing

The same place can assert. This is where API testing starts, and week 13 builds on it:

```js
pm.test("created", () => pm.response.to.have.status(201));

pm.test("returns an id", () => {
  pm.expect(pm.response.json().id).to.be.a("string");
});

pm.test("amount matches what we sent", () => {
  pm.expect(pm.response.json().amount).to.eql(4850000);
});
```

That third one is the field-by-field comparison from week 6, automated. It runs on every send and catches the money bug that a screen renders perfectly.

<Callout kind="job">
Add one assertion to every request you save: **the status you expect**. It costs ten seconds and turns a collection from a set of things you can send into a set of things that tell you when they break.

Run the whole collection and Postman reports pass and fail per request. That is a smoke test, and you just built one without meaning to.
</Callout>

## Running a whole collection

**Collection → Run.** Postman sends every request in order and reports the results.

Two things make this genuinely useful:

- It respects the current **environment**, so the same sequence runs against sandbox or production — deliberately, with the target named.
- It runs in **order**, so chained values flow through.

This is your first automated test suite. It is not Playwright, and it does not need to be: a ten-request collection with a status assertion on each is a real regression check you can run in thirty seconds after any deploy.

## Where chaining goes wrong

**A stale variable.** The token from yesterday is still in the environment and expired overnight. Everything returns 401 and nothing looks wrong. Clearing variables between runs avoids an afternoon of confusion.

**A value that does not exist.** The script reads `body.token` but the response nests it as `body.data.token`, so the variable is set to `undefined` and later requests send the literal string. Log it once to check.

**Assuming order where there is none.** Collection Runner is ordered; your own memory is not. If a request only works after another, say so in its description.
