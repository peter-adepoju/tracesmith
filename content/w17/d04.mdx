One question routes a ticket correctly on the first attempt: **did a request leave the browser, and what came back?**

Ten seconds in the Network panel answers it.

## The four outcomes

<NetworkVerdict />

Work through all four. The customer's description is identical in every case — *it didn't work* — and the correct team is different each time.

## The decision

```
Open Network, reproduce, look.

No request at all
  → Front end. Check the console; something threw first.
     Nothing will be in the server logs. Do not look there.

Request, status 4xx
  → The server refused it, correctly or not.
     Read the response body — it usually says exactly why.
     If the refusal is right, the bug is the message the page showed.
     If the refusal is wrong, it is back end.

Request, status 5xx
  → Back end. Get the request id from the response headers.

Request, status 2xx, screen says it failed
  → Front end, and urgent.
```

## No request is the expensive one

Nothing arrived, so there is nothing in the server logs — and a support agent who assumes the server must know can spend half an hour searching for an event that never existed.

Causes: a JavaScript error before the call, a disabled button, a form that never submitted, a network failure, an extension or ad-blocker eating the request, a CORS failure.

The console almost always has it.

## The 2xx that says it failed

The worst of the four, because it is the only one that **gets worse while you think about it**.

The payment succeeded. The customer was told it failed. They will try again — and now there is a duplicate charge on top of a display bug, and the second problem is one you could have prevented by replying faster.

So when you see this pattern, the first message is not to the engineer. It is to the customer: *"Your payment of NGN 48,500 did go through — reference PAY-8841. Please do not try again. The screen showed an error incorrectly and we are fixing that."*

<Callout kind="key">
**Status plus screen, together.**

Neither alone is enough. A `200` does not mean the customer was served; a failure message does not mean anything failed. The contradiction between them *is* the diagnosis, and it is the one a customer can never report because they cannot see the status.
</Callout>

## Other things the panel tells you

**Timing.** A 30-second request that then failed is a timeout — a different problem from an instant rejection, and a different team.

**The response body.** A 4xx almost always explains itself. The page threw the explanation away; you do not have to.

**Request headers.** Was the `Authorization` header sent at all? A missing one explains a 401 immediately.

**Repeats.** The same request four times in two seconds is a double-submit or a retry loop, and that is its own bug.

## Routing

| Evidence | Owner |
| --- | --- |
| No request, console error | Front end |
| 4xx with a clear body, generic message on screen | Front end (the message) |
| 4xx that should have succeeded | Back end |
| 5xx | Back end, with the request id |
| 2xx, screen says failure | Front end, urgent |
| Timeout after 30s | Back end or infrastructure |
| Request not sent due to CORS | Front end or infrastructure |

Put the evidence in the escalation, not the conclusion alone. *"Front-end issue"* invites an argument; *"POST returned 201 with reference PAY-8841 at 14:02 and the page displayed 'Payment failed'"* does not.
