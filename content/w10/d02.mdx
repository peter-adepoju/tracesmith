Preconditions are the state the world must be in before step 1. They are the least glamorous part of a test case and the one that decides whether anyone else can run it.

## What they cover

**Which environment.** Sandbox, staging, production-read-only. Never assume.

**Who you are.** Not "a user" — *which* user, with which role and which permissions. "Signed in as a merchant whose KYC is approved" is a precondition. "Logged in" is not.

**What exists.** Product A is in stock. The customer has at least one past order. The discount code `SAVE10` is active and unused.

**What does not exist.** The cart is empty. This email has never signed up. There are no saved addresses.

**Configuration.** Test keys set. The feature flag is on. The webhook URL points at the test receiver.

<Callout kind="key">
The question to ask of every precondition: **would this case behave differently if this were not true?**

If yes, it is a precondition and must be stated. If no, leave it out — a precondition list that includes everything is as unusable as one that includes nothing.
</Callout>

## The absent-precondition bug

It looks like this:

> The case passes for you, every time. It fails for a colleague, every time. Nobody can work out why.

Because your account has a saved card and theirs does not. Because you have three past orders and they have none. Because you are on staging and they are on dev.

**That gap is the missing precondition.** When a case passes for one person and fails for another with no code change between them, you have found a state difference the case failed to state — and finding it is itself worth writing down.

## Setup: getting to the starting state

Preconditions describe the state. Setup is how you reach it.

Three approaches, in increasing order of reliability:

**By hand.** Click through to create what you need. Fine once; miserable the fortieth time.

**Through the API.** Create the order with Postman instead of six screens. Faster, repeatable, and you built exactly this in week 8 — this is where that collection starts paying for itself.

**From a fixture.** A known dataset loaded before the run, so everyone starts identically. The best option, and usually a team-level decision rather than yours.

<Callout kind="job">
If a case needs fifteen clicks of setup before the thing you are actually testing, **create that state through the API instead.** You are not testing the setup; you are testing what happens next.

It turns a ten-minute case into a one-minute case, which means you will actually run it during retesting rather than quietly skipping it. A case too tedious to re-run is a case that stops being run.
</Callout>

## Cleanup

What you leave behind becomes the next run's problem. Three options, same as week 9:

- **Unique data per run** — `peter+20261107@example.com`. Simplest, and nothing needs undoing.
- **Delete what you made** — reliable until a case fails halfway and leaves debris.
- **Reset the environment** — cleanest, usually someone else's job.

If a case cannot be run twice in a row without failing, say so in the case. A note reading *"uses a fresh email each run; the previous one cannot be reused"* saves the next person twenty minutes.

## Writing them well

| Weak | Strong |
| --- | --- |
| Logged in | Signed in as a merchant with KYC approved, on staging |
| Some products exist | Product A in stock (qty > 5); Product C out of stock |
| A discount code | `SAVE10` active, 10%, unused by this account |
| Test environment | Staging, test keys set, webhook pointing at the test receiver |

The strong column takes thirty seconds more to write and removes an entire category of "works for me".
