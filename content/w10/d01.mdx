A test case is one small, repeatable test written so that **anyone can run it and get the same answer**. That last part is the whole definition, and it is the part beginners skip.

## The seven parts

```
ID:            PAY-001
Title:         Card payment of NGN 1,000 succeeds in the sandbox
Preconditions: Verified test merchant; test public key set; Product A in stock
Steps:         1. Add Product A to the cart on the test store
               2. Go to the cart and click Checkout
               3. Choose Card and enter the Interswitch test card
               4. Enter the test OTP and submit
Expected:      Transaction shows status Success, amount NGN 1,000, channel Card;
               the order is marked paid
Actual:        (filled in when run)
Status:        Pass / Fail / Blocked
```

**ID** — stable, so you can refer to it in a bug report, a run and a conversation. "The third one" survives none of those.

**Title** — readable on its own in a list of two hundred.

**Preconditions** — what must already be true. Tomorrow.

**Steps** — numbered, one action each. Day 3.

**Expected result** — the observable outcome. Day 4, and it is where most cases fail.

**Actual** and **Status** — filled in when you run it.

## The test of a good case

> Could someone who has never seen this product run it and reach the same conclusion?

If a step says "log in" and they do not know as whom, your case is incomplete. If the expected result says "it works correctly", they cannot tell whether it did.

<Callout kind="key">
**A case that only you can run is a note to yourself.** That is fine in exploratory work, where notes are the output. It is not a test case.

The difference matters because test cases outlive you: they run after you leave, they get handed to a new joiner, and they become the regression suite nobody remembers writing.
</Callout>

## What makes a bad case

**Too big.** "Test the checkout" is not a case, it is an area. One case checks one thing, so that a failure tells you precisely what broke.

**Dependent on the last one.** Case 7 assuming case 6 just ran means it cannot be run alone, and a failure in 6 cascades into false failures. Each case stands up by itself, with preconditions doing the setup.

**Vague expected results.** "The page works." Unfalsifiable, therefore useless.

**Describing the interface instead of the goal.** "Click the blue button at the top right" breaks when the design changes. "Click **Checkout**" survives it.

**Only the happy path.** A suite of twenty cases where all twenty pass on a working feature has told you one thing. Half your cases should be trying to break it.

<Callout kind="job">
The commonest real failure is the second one. A tester writes twelve cases in order, each continuing from the last, and it works beautifully — until someone runs case 9 on its own and it fails for no reason, or case 3 breaks and nine others go red with it.

**Write each case so it can be run alone, in any order.** It takes slightly longer and saves days.
</Callout>

## Where they live

A spreadsheet is completely respectable, and many good teams use one: ID, title, preconditions, steps, expected, actual, status, notes.

Dedicated tools — TestRail, Zephyr, Xray, Qase — add run history, linking to tickets and reporting. Useful at scale, and not a prerequisite.

What matters is that cases are **written down, shared, and have a recorded result per run.** A suite in one person's head is not a suite.
