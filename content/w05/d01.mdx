Phase 1 taught you to read what comes back. Phase 2 teaches you to read it precisely, and then to send your own.

Almost every API response you will ever see is JSON. This week is about reading one with confidence, which sounds small and is not: most support tickets are settled by one person reading a response carefully.

## Why HTML is the wrong answer

You already know one format a server sends: HTML. It works beautifully for a page and badly for data, because it describes *presentation*.

Imagine asking a server for one customer and getting back:

```html
<div class="customer">
  <span class="label">Name:</span>
  <span class="value">Ada Obi</span>
</div>
```

To get the name, a program must find the right `<span>`, in the right position, inside the right `<div>` — and all of that breaks the moment a designer moves something. People have genuinely built systems this way. It is called scraping, and it is miserable.

What a program wants is:

```json
{ "name": "Ada Obi" }
```

No presentation. No ambiguity. One name, one value.

<Callout kind="key">
This is the distinction: **HTML is for a human to look at, JSON is for a program to use.** The same server often sends both — HTML to your browser, JSON to the page's own scripts. That is exactly what you saw in the Network tab, where `Doc` and `Fetch/XHR` are two different kinds of answer.
</Callout>

## The formats you will meet

| Format | Where you meet it |
| --- | --- |
| **JSON** | Almost every modern API. This week. |
| **XML** | Older systems, banking, SOAP services. Angular-bracketed and verbose. |
| **CSV** | Spreadsheet exports, bulk uploads. Rows and commas, no nesting. |
| **Form-encoded** | What a plain HTML form submits: `name=Ada&qty=2` |
| **Multipart** | File uploads. |

You need to recognise all five and read one fluently. JSON is the one.

## A whole document

```json
{
  "status": "success",
  "data": {
    "reference": "ORDER-1001",
    "paid": true,
    "amount": 4850000,
    "customer": { "name": "Ada Obi" },
    "items": [
      { "sku": "mer-01", "qty": 1 }
    ]
  }
}
```

You can probably already read that, which is the point — JSON is deliberately small. The whole syntax is tomorrow's lesson and it genuinely fits in one day.

Two things in there are worth noticing now, because both cause real bugs:

**`"amount": 4850000`** is not forty-eight million. It is **minor units** — kobo, cents, pence — so it means ₦48,500.00. Storing money as a whole number of the smallest unit avoids the rounding errors that floating-point decimals cause. When an amount looks absurd by a factor of a hundred, this is almost always why.

**`"paid": true`** is a boolean, not the string `"true"`. They look similar and behave differently, and a system that checks `if (paid === "true")` against a real boolean silently never matches.

<Callout kind="job">
"The amount is wrong by 100x" is one of the most common support reports in payments, and it is usually not a bug: it is somebody reading minor units as major. Knowing to check is worth a lot, and so is knowing when it genuinely *is* the bug, because the reverse mistake charges someone a hundred times too much.
</Callout>
