A schema is the promise an API makes about the shape of its answers. Knowing how to read one turns "that looks odd" into "that violates the contract", which is a much stronger thing to say.

## What a schema says

```json
{
  "type": "object",
  "required": ["reference", "amount", "currency", "paid"],
  "properties": {
    "reference": { "type": "string" },
    "amount":    { "type": "integer", "minimum": 1 },
    "currency":  { "type": "string", "enum": ["NGN", "USD", "GHS"] },
    "paid":      { "type": "boolean" },
    "email":     { "type": ["string", "null"], "format": "email" }
  }
}
```

Read in plain words: this is an object; four fields must be present; `amount` is a whole number of at least 1; `currency` must be one of three values; `email` may be a string or null, and when it is a string it must look like an address.

You will not often write these. You read them constantly, because they tell you **what to test**:

- Every `required` field is a test: what happens when it is missing?
- Every `enum` is a test: what happens with a value not on the list?
- Every `minimum` is a boundary: test it, and one below it.
- Every `["string", "null"]` tells you null is expected, so the page must handle it.

<Callout kind="key">
A schema is a **test plan someone else already wrote for you.** Each constraint is a case, and the negative case is usually the interesting one. This is where week 10's test-case writing and week 13's API testing meet.
</Callout>

## Where you find one

| Source | What you get |
| --- | --- |
| **OpenAPI / Swagger** | The common one. A whole API described, often with a "Try it" console |
| **A JSON Schema file** | The shape alone, as above |
| **Typed client code** | TypeScript types are a schema in another costume |
| **The docs page** | A table of fields and types. Informal, and still a contract |
| **Nothing at all** | Common. Then the *observed* shape is the only contract, which is a finding in itself |

## Comparing a response against its promise

The method is mechanical, and worth doing in this order:

1. **Required fields.** Is every one present? Absent is a contract violation; `null` is only one if the schema does not allow null.
2. **Types.** Is `amount` a number, or the string `"4850000"`? Is `paid` a boolean or `"true"`?
3. **Values.** Inside the enum? Above the minimum? A plausible date?
4. **Extra fields.** Not usually a bug, but worth noticing — an unexpected `internal_notes` or `debug_token` in a public response is a real finding.

<Callout kind="job">
Point 4 is where security findings hide. Compare what the schema promises with what actually arrives, and look for the **extra**. An internal flag, a hashed password, another customer's id, a stack trace. The page never shows them; the response contains them. This becomes one of the five security checks in week 14.
</Callout>

<Callout kind="watch">
Work them out before reading on.

**`amount` is a string**, not an integer. Arithmetic on it will concatenate rather than add — a classic way to get a nonsense total.

**`currency` is `"EUR"`**, which is not in the enum. Either the enum is out of date or the server is wrong, and both matter.

**`paid` is absent**, and it is required. The page has no way to know whether this order was paid.

**`internal_risk_score` and `reviewer_note` should not be here at all.** A note explicitly saying "do not surface" is being sent to the browser, where anyone can read it. That is the finding to escalate first, and the screen would never have shown you it.
</Callout>
