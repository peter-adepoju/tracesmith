JSON is a genuinely small language. Six types, two containers, and a handful of punctuation rules. You can learn all of it today.

## The six types

```json
{
  "aString": "text, always in double quotes",
  "aNumber": 4850000,
  "aBoolean": true,
  "nothing": null,
  "anObject": { "nested": "values" },
  "anArray": [1, 2, 3]
}
```

**String** — double quotes. Always double, never single. `'Ada'` is invalid JSON.

**Number** — no quotes. Integers or decimals. No leading `+`, no trailing `.`, and **no commas as separators**: `48,500` is invalid.

**Boolean** — `true` or `false`, lowercase, no quotes. `True` is invalid; `"true"` is a string, which is a different thing.

**Null** — `null`, lowercase. Deliberately empty.

**Object** — `{ }`. A set of key-value pairs. Keys are **always quoted strings**.

**Array** — `[ ]`. An ordered list. Items may be any type, including mixed.

That is the entire language.

## The punctuation rules that actually trip people

**Every key is quoted.** `{ name: "Ada" }` is valid JavaScript and invalid JSON. This catches people constantly, because the two look nearly identical.

**Commas separate, they do not terminate.** The last item takes no comma:

```json
{
  "a": 1,
  "b": 2
}
```

A **trailing comma** after `2` is invalid. This is the single most common cause of a 400 from a JSON API, and you met it in week 1.

**No comments.** `//` and `/* */` are not allowed. A config file that accepts them is not JSON, whatever its extension says.

<Callout kind="watch">
Those three rules explain nearly every "Bad Request" you will ever diagnose on a JSON body: an unquoted key, a trailing comma, or a single quote. When a developer swears their JSON is fine, ask them to paste it into a validator. It usually is not.
</Callout>

## Numbers deserve a warning

```json
{
  "amount": 4850000,
  "rate": 1.5,
  "big": 9007199254740993
}
```

Two traps.

**Very large numbers lose precision.** JavaScript can represent integers exactly only up to about nine quadrillion. Beyond that, digits change silently. This matters for long identifiers: a 19-digit account number sent as a JSON *number* can come back altered. Which is why good APIs send identifiers as **strings**, even when they look numeric.

**Decimals are not exact.** `0.1 + 0.2` is `0.30000000000000004` in essentially every language. That is why money is sent in minor units as a whole number rather than as `48500.00`.

<Callout kind="job">
If you see `"accountNumber": 3012345678` as a number rather than a string, that is worth raising. Leading zeros are also lost — `0123456789` becomes `123456789` — and Nigerian account numbers can begin with a zero. It is a real defect with a quiet failure mode.
</Callout>

## Whitespace and formatting

JSON ignores whitespace between tokens, so these are identical to a parser:

```json
{"a":1,"b":2}
```

```json
{
  "a": 1,
  "b": 2
}
```

Real APIs send the first, to save bytes. DevTools pretty-prints it for you in the **Preview** tab — which is exactly why Preview exists alongside Response.
