Four states look like "nothing" and mean four different things. Telling them apart is one of the highest-value things in this week, because the difference decides whose bug it is.

## The four

```json
{
  "a": null,
  "b": "",
  "c": [],
  "d": 0
}
```

Plus a fifth that is not in the document at all: **the key is absent**.

| State | Means | Who to ask |
| --- | --- | --- |
| **Absent key** | The server did not send this field | Back end: was it meant to? |
| **`null`** | The field exists and is deliberately empty | Back end: why is it empty? |
| **`""`** | A string that is present and blank | Usually validation: should blank be allowed? |
| **`[]`** | A list with genuinely no items | Normal. Handle it. |
| **`0`** | A real number, which happens to be zero | Normal, and not "nothing" |

<Callout kind="key">
**Absent and null are not the same.** Absent means the server never mentioned it. Null means the server mentioned it and told you it is empty.

That distinction routinely decides ownership. A missing key is often a back-end bug or an API version mismatch. A null is usually correct behaviour the front end failed to handle.
</Callout>

## Zero is the dangerous one

```json
{ "balance": 0, "itemCount": 0, "discount": 0 }
```

Many languages treat `0` as false in a plain truthiness check. So code written as *"if there is a balance, show it"* hides a zero balance entirely — and the customer sees a blank where they should see ₦0.00.

The same bug hides an empty string, an empty array, and `false`.

<Callout kind="watch">
This is behind a whole family of real defects:

- A zero balance renders as blank instead of ₦0.00
- A "0 items" state shows nothing rather than "no items"
- A discount of 0 is skipped, so the line vanishes from a receipt
- `false` in a settings list makes the row disappear instead of showing "off"

Test with zero. Test with an empty string. Test with `false`. These are not edge cases; they are Tuesday.
</Callout>

## How to report each one

The wording matters, because it tells the reader where to look.

> **Absent:** "The response for ORDER-1002 has no `customer.phone` key at all. The API docs list it as always present."

> **Null:** "`customer.email` is `null` for ORDER-1002, so the confirmation has nowhere to go. Should a paid order be able to have no email?"

> **Empty string:** "`customer.name` is `""` — the signup accepted a blank name. Server-side validation is missing."

> **Empty array:** "`items` is `[]` on a paid order. Either the order is genuinely empty, which should not be possible, or the items failed to attach."

Each one points at a different team and a different question. That is the whole value of knowing the difference.
