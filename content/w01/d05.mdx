A request has a body — sometimes. It always has headers.

Headers are the information *about* the message rather than the message itself. If the body is the letter, the headers are everything written on the envelope: who it is from, what language it is in, how to handle it.

## The shape

A header is a name, a colon, and a value. One per line.

```http
Content-Type: application/json
Authorization: sk_test_trace_93ba07
Accept: application/json
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
```

Header names are case-insensitive: `Content-Type` and `content-type` are the same header. You will see both styles and neither is wrong.

Both requests and responses have them. They are not the same set.

## Request headers worth knowing

**Authorization** — your credential. A key, or a token. This is the single most sensitive thing in a request and we will come back to it.

**Content-Type** — what format the body is in. `application/json` for JSON, `application/x-www-form-urlencoded` for a plain HTML form, `multipart/form-data` for a file upload.

**Accept** — what format you would *like* back. A server may offer JSON and HTML for the same endpoint and use this to choose.

**User-Agent** — what software is making the request. This is how analytics knows your browser, and how a server can behave differently for a bot.

**Cookie** — small values the browser stores and sends back automatically. Usually how a logged-in session is carried.

<Callout kind="watch">
`Content-Type` and `Accept` are easy to confuse. **Content-Type describes what you are sending. Accept describes what you want back.** Sending JSON while declaring `Content-Type: text/plain` is a classic cause of a 400 that looks inexplicable, because the server refuses to parse a body you did not label as JSON.
</Callout>

## Response headers worth knowing

**Content-Type** — what format the body you are receiving is in.

**Content-Length** — how big it is.

**Set-Cookie** — the server asking your browser to store something and send it back next time. This is how logging in works.

**Cache-Control** — how long this answer may be reused before asking again.

**x-request-id** (and similar) — an identifier for this exact request in the server's logs. Not a standard header, but almost every serious API has one under some name.

<Callout kind="job">
That request id is the most useful thing you can put in an escalation. "It's failing" makes an engineer search. "Request id req_8fa0c21b at 14:32 UTC returned 500 on POST /v1/payments/initiate" lets them pull up the exact failure in one query. Always look for it, and always include it.
</Callout>

## The part that gets people fired

The `Authorization` header is a password. Treat it exactly as you would treat one.

It will appear, in full, in:

- A DevTools screenshot of the Headers tab.
- A "Copy as cURL" command pasted into a ticket.
- A HAR file exported from the Network tab.
- A screen recording where you scrolled past it.

Every one of those is a normal thing a tester or support engineer does every day, and every one of them leaks a live credential if you are not deliberate.

<Callout kind="watch">
**Redact before you share. Every time.**

Black out the value in screenshots. Replace it with `REDACTED` in any pasted command. Before attaching a HAR file, strip it, or do not attach it at all.

The same goes for anything in the body: card numbers, bank details, national identity numbers, one-time codes. Your evidence must prove the bug, not become a second incident.
</Callout>

And the other direction: **never ask a customer to send you their key, password, or one-time code.** If they volunteer one, stop them, tell them plainly that the value is now compromised, and help them rotate it. A customer handing you a secret is a customer trying to be helpful; protecting them from it is part of the job.

## Reading headers in the inspector

<RequestInspector preset="Verify a payment" />

Press Send, then open the **Headers** tab. You are looking at the same three blocks a real browser shows: the General section with the URL, method and status; the request headers; and the response headers.

Notice `x-request-id` in the response. That is the value you would quote.
