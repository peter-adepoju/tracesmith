The last week of Phase 3, and the one that changes what you are worth on the market. But it starts with the honest part, because the industry's enthusiasm for automation has a cost nobody mentions in the job advert.

## Automation is not free

Writing a test is the cheap bit. Then:

- It has to be **maintained**. Every change to the product may break it.
- It has to be **trusted**. A test that fails randomly is worse than no test.
- It has to be **run**, in CI, and someone must look when it is red.
- It **finds nothing new**. An automated test only ever checks what you told it to, forever. It never notices that the page looks wrong.

<Callout kind="key">
**Automation does not find bugs. It finds regressions.**

A human exploring finds bugs. An automated suite tells you that the things you already knew about still work. Those are different jobs, and a team that replaces the first with the second stops finding anything new.

The value is in the repetition: running 200 checks in four minutes on every push, which no person can do, so the person is free to go and look for what nobody has thought of yet.
</Callout>

## What to automate

Score a candidate on four questions:

**How often does it run?** A smoke test on every push, dozens of times a day, is the strongest case there is. Something run once a quarter is not.

**How stable is it?** A checkout flow that has worked the same way for two years will keep passing. A screen being redesigned next sprint will cost you a rewrite before it has ever caught anything.

**How costly is the failure?** Payment, sign-in and data integrity justify effort that a footer link does not.

**How deterministic is it?** Does it give the same answer every time? If the result depends on timing, third-party services or the date, you are signing up for maintenance.

The obvious yes: **smoke tests, regression suites, API checks, boundary values, cross-browser repeats of one critical flow.**

## What to keep manual

Three things, and be able to say them in an interview:

**Exploratory testing.** The whole point is that nobody knew what to look for. Automation can only check what was already imagined.

**Usability and visual judgement.** "Is this confusing?" has no assertion. A machine can tell you a button is 4px lower; it cannot tell you the flow makes no sense.

**Anything changing fast.** A feature in active design costs more to keep green than it returns. Automate it when it settles.

And a fourth worth adding: **a one-off check.** If this will be run twice, run it twice by hand.

<Callout kind="job">
When an interviewer asks what to automate, the weak answer is "everything". The strong answer names the trade-off: repetition and stability against maintenance cost, plus the three things you deliberately keep manual and why.

That answer alone separates a tester who has automated something from one who has read about it.
</Callout>

## The pyramid, and why it is shaped that way

```
        /\        A few end-to-end tests
       /  \       Slow, realistic, flaky, expensive to maintain
      /----\
     /      \     More API tests
    /        \    Fast, stable, no browser
   /----------\
  /            \  Many unit tests
 /______________\ Milliseconds, written by developers
```

Each layer up is slower, more brittle and more expensive. So: test a thing at the **lowest layer that can see it** — the same rule as week 13.

The common failure is the **ice cream cone**: a hundred end-to-end tests and almost nothing below. It takes forty minutes to run, fails for unrelated reasons twice a week, and the team learns to re-run it rather than read it.

<Callout kind="watch">
**A flaky suite is worse than no suite.** Not slightly worse — actively harmful.

Once people learn that red sometimes means nothing, they stop reading red. The suite still runs, still costs money, and no longer protects anything; and the day it catches a real defect, somebody re-runs it and ships.

So: a test that cannot be made reliable should be deleted, not tolerated. That is a real decision you will have to argue for.
</Callout>
