You have been reading API responses for five weeks. This week is about the thing producing them.

"API" is one of those terms people use confidently without ever being told what it means. Here is the plain version.

## The one-sentence answer

**An API is a way for one program to ask another program to do something.**

That is it. Not a technology, not a product — an agreement. One system publishes a set of things it will do and how to ask for them; another system asks.

## Three everyday examples

**A shop that accepts cards.** The shop's own software does not know how to talk to banks. It asks a payment company's API: *"charge this card ₦48,500."* The API answers success or failure. The shop never touches a bank.

**A weather widget.** It does not forecast anything. It asks a weather service's API *"what is the weather in Lagos?"* and displays the answer.

**Signing in with Google.** The site does not see your Google password. It asks Google's API *"is this person who they claim to be?"* and Google answers.

In each case the pattern is the same: **someone else has solved a hard problem, and the API is the door into their solution.**

## Why a company publishes one

Worth understanding, because it tells you what an API is optimised for.

- **It is the product.** A payment company's API *is* what you buy. There is nothing else.
- **Their own apps need one.** The phone app, the website and the back office all need the same data. Build one API, serve all three. This is why most sites have an internal API you can see in the Network tab.
- **Partners need in.** A marketplace lets sellers manage stock programmatically rather than by hand.

That second one matters to you. **The API you will test most is the one the product uses to talk to itself**, and it was often never designed to be seen by outsiders — which is exactly why interesting things leak out of it.

<Callout kind="key">
Every `Fetch/XHR` row you saw in week 4 was an API call. You have been watching APIs all along without naming them. The only new thing this week is that you will start *making* the calls instead of watching them.
</Callout>

## The vocabulary, laid out once

| Word | Means |
| --- | --- |
| **API** | The whole agreement: everything this system will do for you |
| **Endpoint** | One specific address you can call. Tomorrow |
| **Request** | What you send |
| **Response** | What comes back |
| **Payload / body** | The data carried inside a request or response |
| **Parameter** | A value you supply to shape the request |
| **Authentication** | Proving who you are. Week 7 |
| **Rate limit** | A cap on how often you may call |
| **Client** | Whoever is calling |
| **Provider** | Whoever answers |

You already know most of these from Phase 1. They were always API words.

## The distinction that confuses everyone

**API** and **endpoint** are not the same, and people use them interchangeably.

An API is the whole service. An endpoint is one door into it.

```
The API:          the payment service
Its endpoints:    POST /v1/payments/initiate
                  GET  /v1/payments/verify/{reference}
                  GET  /v1/customers
                  GET  /v1/customers/{id}
```

One API, four endpoints. When someone says "the API is down", ask **which endpoint** — it is very often one of them, not all. That single question has saved many hours.

<Callout kind="job">
A merchant reporting "your API is broken" is giving you almost nothing. The useful reply asks for one thing: the endpoint and the status code. "Which call, and what came back?" turns an outage report into a specific, checkable claim — and about half the time it turns out one endpoint is returning 422 because they are sending the wrong field.
</Callout>
