A request can carry a value in three places. Choosing the wrong one is not a style question — it produces real bugs, including values that silently never arrive.

<Video id="path-vs-query" />

## The three places

**Path parameter** — part of the address. Identifies *which* resource.

```
GET /v1/customers/cus_01
                  ───────
```

**Query string** — after the `?`. Modifies *how* you want the answer.

```
GET /v1/orders?status=paid&limit=25&sort=-created
               ──────────────────────────────────
```

**Body** — sent inside the request, usually JSON. The data you are *submitting*.

```
POST /v1/orders
{ "customerId": "cus_01", "items": [...] }
```

## The rule for choosing

| Ask | Then it belongs in |
| --- | --- |
| Does it identify which thing? | **Path** |
| Does it filter, sort, page or shape the result? | **Query** |
| Is it data you are sending to be stored or acted on? | **Body** |

A useful test for path versus query: **remove it. If the request no longer makes sense, it was a path parameter. If it still makes sense but returns more, it was a query parameter.**

`/v1/customers/cus_01` without `cus_01` becomes `/v1/customers` — still meaningful, returns all. So arguably either. But `/v1/payments/verify/ORDER-1001` without the reference is meaningless, so that one is firmly a path parameter.

<Callout kind="watch">
Three real bugs come out of getting this wrong.

**A body on a GET.** Technically allowed, and widely discarded — caches, proxies and many server frameworks drop it. The value simply never arrives, and nothing errors. The builder above flags this one.

**Sensitive data in a query string.** URLs are logged everywhere: server logs, proxy logs, browser history, the `Referer` header sent to third parties. A password, a token or a card number in a query string has been written to half a dozen places you do not control. **This is a genuine security finding**, and a common one.

**Unencoded characters.** A value containing `&`, `?`, `=`, `#` or a space breaks the URL unless it is percent-encoded. `note=Ada & Bola` silently becomes a `note` of `Ada ` plus an empty parameter called `Bola`.
</Callout>

## Encoding, briefly

```
?note=Ship before Friday     wrong, spaces break it
?note=Ship%20before%20Friday correct
?q=a%26b                     an actual & in the value
```

You will rarely encode by hand — Postman and every HTTP library do it. You need to **recognise** it, so that `%20` and `%40` in a log do not look like corruption. `%40` is `@`, which is why you see it in emails passed through URLs.

<Callout kind="job">
A merchant reports that customer names with apostrophes or accents are saved wrong. Check whether the value travels in a query string and whether it is being encoded. `O'Brien` and `Adébáyọ̀` break more systems than anyone expects, and this is one of the two usual causes — the other is a character-encoding mismatch, from week 2.
</Callout>
