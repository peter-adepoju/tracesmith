This is the most valuable thing a tester produces. Not the bug — the report.

The standard is one sentence long: **an engineer should be able to act on it without asking you anything.**

## The shape

```
Title       Applying the same discount code twice stacks the reduction (cart)

Environment Meridian sandbox, stage 3 · Chrome 131 · desktop · 7 Nov 14:12

Steps       1. Add Harmattan Field Jacket to the cart
            2. Open the cart
            3. Enter SAVE10 and click Apply
            4. Enter SAVE10 again and click Apply

Expected    The second application is refused with a message that the code
            is already applied; the total stays at NGN 43,650.00

Actual      The second application is accepted and the discount becomes 20%.
            The total drops to NGN 38,800.00. Repeating reaches NGN 0.00
            after ten applications.

Evidence    Screenshot of the cart after two applications (attached).
            Network: POST /api/meridian/orders shows discountMinor growing
            on each apply. No credentials in the capture.

Severity    Critical          Priority  Highest
Why         Anyone who notices can take goods for free. No workaround;
            the only control is not telling customers.
```

Read it as an engineer: you know what to do, where to go, what you will see, and what it should have been. Nothing is missing, and you did not have to ask.

## The title does most of the work

It is read in a list of a hundred, in a notification, in a stand-up. It should carry the bug on its own.

| Weak | Strong |
| --- | --- |
| Discount bug | Same discount code can be applied repeatedly, stacking the reduction |
| Cart broken | Cart total ignores quantity for items added twice |
| Payment issue | Double-clicking Place order creates two orders and charges twice |
| 500 error | POST /v1/payments/initiate returns 500 for amounts over 1,000,000 |

Pattern: **what happens, where, and under what condition.**

## The sentence people leave out

When severity and priority differ, **say why**. One line, and it prevents the argument:

> Critical severity, low priority: only two internal users reach it and exporting in two halves works.

Without it, someone reads "Critical" and "Low" together and comes to ask. With it, the trade-off is visible and agreed.

## Tone

You are describing a system, never a person.

| Avoid | Prefer |
| --- | --- |
| You broke the discount logic | Applying the same code twice stacks the reduction |
| Obviously nobody tested this | Not covered by the existing cases; I have added DISC-003 |
| This is a terrible bug | Critical: the total can be driven to zero |
| Why does this keep happening? | This is the third discount defect this sprint — worth a look at that area? |

The right-hand column gets fixed faster. Not because engineers are fragile, but because a report that reads as an accusation invites a defence, and a defence is a delay.
