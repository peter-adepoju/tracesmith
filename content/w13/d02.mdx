An assertion is a claim your test makes about the response. Get the claims wrong and your suite is green while the product is broken — which is worse than having no suite, because now everyone believes it.

## Three levels

**Status.** Did the call do the kind of thing it should? `200`, `201`, `422`, `404`.

**Schema.** Is the shape right? The fields that must exist, exist; their types are right; money is an integer in minor units, not a float.

**Value.** Are the numbers and strings actually correct? Does `totalMinor` equal `subtotalMinor` minus `discountMinor`?

They are a ladder. Status alone tells you almost nothing — **`200 OK` means the request was handled, not that the answer was right.**

<Callout kind="key">
**The most dangerous test result in software is a green run over a broken build.**

A suite that only asserts on status is exactly that machine. It is fast, it is stable, it never fails, and it tells you nothing — because almost every interesting defect returns `200`.
</Callout>

<AssertionLab />

Start with only *Status is 2xx* selected and run all four scenarios. Three of the four come back green. Then add the schema and value assertions and run them again.

Scenario two is the one to sit with: a correct status, a perfectly correct shape, and a total of zero on a 4,450,000 order. Every structural check passes. Only a value assertion catches it.

## Assertions that fail usefully

A failure should tell you what is wrong without opening anything.

| Weak | Strong |
| --- | --- |
| `assert response.ok` | `expected status 201, got 422 (validation_failed: email)` |
| `assert total > 0` | `expected totalMinor 4450000, got 0` |
| `assert "id" in body` | `expected body.id to be a non-empty string, got undefined` |

The pattern: **expected X, got Y, for this field.** If your failure message does not contain the actual value, you will be re-running the test by hand to find out what it was.

## What to assert on, every time

A reasonable default for any endpoint:

1. **Status** — the exact one documented, not merely 2xx
2. **Required fields present**, with the right types
3. **Money is an integer** in minor units
4. **The arithmetic** — totals, counts, sums
5. **Identifiers** are non-empty and in the documented format
6. **Timestamps** are valid and in the documented timezone
7. **The side effect** — did the thing actually get created, changed or removed?

Seven claims. Most of them are two lines each.

<Callout kind="watch">
**Do not assert on everything.** A test that asserts on all forty fields of a response fails every time anyone adds a field, and a test that cries wolf gets ignored or deleted.

Assert on what the endpoint promises and what this test is about. A test named *rejects an invalid email* should not fail because an unrelated field was renamed.
</Callout>
