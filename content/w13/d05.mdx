You do not need to be a database engineer. You need `SELECT`, and about an hour.

## The shape of a query

```sql
SELECT   name, price_minor      -- which columns
FROM     products               -- which table
WHERE    category = 'Bags'      -- which rows
ORDER BY price_minor DESC       -- in what order
LIMIT    10;                    -- how many
```

Always in that order. `SELECT *` gives you every column, which is fine while exploring and noise in a report.

## WHERE

```sql
WHERE status = 'paid'
WHERE total_minor > 5000000
WHERE email LIKE '%@example.com'
WHERE city IN ('Lagos', 'Abuja')
WHERE created_at >= '2026-10-01'
WHERE discount_code IS NULL
WHERE status = 'paid' AND total_minor > 5000000
```

Three traps worth knowing before they cost you an hour:

- **Strings take single quotes.** `'Lagos'`, never `"Lagos"`.
- **`NULL` is not a value.** `= NULL` matches nothing, ever. Use `IS NULL`.
- **`LIKE` wildcards** are `%` for any run of characters and `_` for exactly one.

## JOIN

Orders hold a `customer_id`, not a name. To see both, join:

```sql
SELECT o.id, c.name, o.total_minor
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid';
```

`JOIN` keeps only rows that match on both sides. `LEFT JOIN` keeps every row from the left table and fills the right with `NULL` where there is no match — which is how you find orphans:

```sql
SELECT o.id
FROM orders o
LEFT JOIN customers c ON c.id = o.customer_id
WHERE c.id IS NULL;        -- orders whose customer does not exist
```

That query is a data-integrity check, and finding a row is a real bug.

## Counting and grouping

```sql
SELECT COUNT(*) FROM orders WHERE status = 'paid';

SELECT c.name, COUNT(*) AS n
FROM orders o
JOIN customers c ON c.id = o.customer_id
GROUP BY c.id
ORDER BY n DESC;
```

`WHERE` filters rows before grouping; `HAVING` filters groups after. That distinction is what the last task below is built on.

## The rules for touching real data

<Callout kind="watch">
You will eventually be given access to a real database. Before you are:

1. **Read-only, always.** Ask for a read-only account. If you are handed one that can write, say so and ask for the right one — it protects you as much as the data.
2. **Never UPDATE or DELETE in production.** Not to set up a test, not "just this row". If a test needs data, ask for a seeding script or a sandbox.
3. **`SELECT` before anything else.** If you ever do have to change something on a non-production database, run the `SELECT` with the same `WHERE` first and look at exactly which rows come back.
4. **`LIMIT` while exploring.** A `SELECT *` over fifty million rows will hurt a production database, and that is an outage you caused.
5. **Personal data is personal data.** The same redaction rules as week 11. Customer names and emails do not go in a ticket; the customer id does.
</Callout>

A `DELETE` with a mistyped `WHERE` is the classic career-defining accident, and it is nearly always someone who meant well and was in a hurry.
