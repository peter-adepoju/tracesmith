Everything you have tested so far, you tested through a screen. This week you go underneath it — because the screen is a rendering of the truth, and a rendering can be wrong in both directions.

## What the screen hides

A page showing the right number is not proof the data is right.

**The screen can be right while the data is wrong.** A page that formats `null` as `NGN 0.00` looks fine and is reporting a missing value as a free order.

**The data can be right while the screen is wrong.** The response carries `totalMinor: 9700000` and the page renders a blank. A UI bug, not a data one — and you cannot tell which from the screen alone.

<Callout kind="key">
Through the UI you are testing **two things at once** — the server and the page — and when it fails you cannot say which one failed.

Testing the endpoint separates them. That is the whole argument for API testing, and it is enough on its own.
</Callout>

## What else API testing buys you

**Speed.** An API call is milliseconds; a UI flow is seconds. The same coverage in a fraction of the time.

**Stability.** Tests through the UI break when a button moves. The endpoint's contract changes far less often.

**Reach.** Some things have no screen at all: a webhook, a scheduled job, an admin endpoint, an error path the UI will not let you trigger. And you can send what the form refuses to type — which is how you find out whether the server validates at all.

**Earlier.** The API is usually finished before the screen that consumes it. You can be testing on Tuesday instead of Friday.

## Which layer does a test belong in?

The useful rule: **test a thing at the lowest layer that can see it.**

| Question | Layer |
| --- | --- |
| Is the discount arithmetic right? | API |
| Does a bad email get rejected? | API — and the UI, separately |
| Is the error message readable by a person? | UI |
| Does the button become disabled while submitting? | UI |
| Does the stock drop after an order? | API, or the database |
| Can a customer complete a purchase? | UI, end to end |

Validation appears twice on purpose. The API test asks *does the server refuse it*; the UI test asks *is the person told what to fix*. Different questions, different layers, and you need both.

## An API test case

Same structure as any test case, with request and response in place of steps and screen:

```
ID          API-ORD-004
Title       Order rejects an email with no @ sign
Precondition  Meridian sandbox, stage 3

Request     POST /api/meridian/orders
            Content-Type: application/json
            { "items": [{"productId":"mer-05","quantity":1}],
              "email": "notanemail" }

Expected    422 Unprocessable Content
            body.error  == "validation_failed"
            body.fields contains "email"
            No order is created (GET /orders count unchanged)
```

That last line is the one beginners leave out. **Assert on the side effect, not only the response.** A server can return a tidy 422 and still have written the row.
