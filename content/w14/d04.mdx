Most endpoints in a product require a signed-in user. Most. The question is which ones were forgotten, and the test is to take the authentication off and send the request anyway.

<Video id="access-tokens" />

## The core test

For every endpoint you know about:

1. Capture a working request — **Copy as cURL** from the Network panel.
2. **Delete the `Authorization` header and the cookies.**
3. Send it.
4. Expect **401 Unauthorized**. Anything else is a finding.

That is the whole test, and on a product of any size it usually finds something — a health endpoint that grew features, an internal admin route nobody listed, a webhook receiver, a file download, a new endpoint added last sprint behind the one piece of middleware it was not wired into.

<Callout kind="job">
Ask a developer for the route list, or read the API documentation, and test **every** route rather than the ones the interface happens to call.

The forgotten endpoint is by definition one the interface does not use. You will not find it by clicking.
</Callout>

## The variations

**No credentials at all.** The base case above.

**An expired token.** Should be `401`. A server that accepts an expired token has effectively issued permanent credentials, and the whole point of expiry is gone.

<TokenInspector />

Load the expired sample and read the `exp` claim. In a real test you would send exactly this and check for a `401`.

**A tampered token.** Decode the payload, change `"role": "customer"` to `"role": "admin"`, re-encode, send. The signature no longer matches, so the server must reject it. A server that does not verify signatures — or honours `"alg": "none"` — is catastrophic, because anyone can mint any identity.

**Another user's valid token.** Legitimate credentials, wrong person. This is yesterday's test, from the authentication side.

**A deactivated account.** The one teams most often miss. Deactivate a user, then send a request with the token they already held. If it still works, deactivation is cosmetic — and that is the token you issued to the person who was dismissed this morning.

**After signing out.** Sign out, then replay a request captured before. The server should have invalidated the session.

<Callout kind="key">
**Deactivation and sign-out are server-side facts or they are nothing.**

A product that clears the token from the browser and calls it signing out has not signed anyone out. The token still exists, it is still valid, and the server will still honour it — it just happens not to be in that browser any more.

Test it by replaying a captured request after signing out. It takes thirty seconds and it is a finding people genuinely miss.
</Callout>

## Password and session hygiene

Checks that need no tools:

- Does **sign-in failure** say the same thing for a wrong password and an unknown email? Different messages let anyone test whether an address is registered. *(You met this from the other side when Tracesmith's own sign-in was failing.)*
- Is there **rate limiting** on sign-in? Ten wrong passwords in five seconds should start being refused with `429`.
- Does the **password reset** link expire, work only once, and become invalid after the password changes?
- Does **changing the password** invalidate other sessions? It should.
- Is the session cookie `HttpOnly`, `Secure` and `SameSite`? Check in the Application panel. `HttpOnly` is the one that stops JavaScript reading it.

<StorageAudit />

A session token in `localStorage` is readable by any script on the page, including one that arrives through a compromised dependency. A cookie marked `HttpOnly` is not.

## Reporting an open endpoint

> **`GET /api/admin/export/customers` requires no authentication.** Sending the request with no `Authorization` header and no cookies returns `200` and a CSV of every customer: name, email, phone, delivery address. Expected `401`. Verified once, with a single request; the file was not retained. Critical: every customer record in the product is downloadable by anyone who knows the path, with no account and no trace in any access log tied to a user. NDPA applies.

Report it the way you would report a leaked credential — through the security channel, immediately, not in a sprint backlog. An unauthenticated data export is the kind of finding that gets a release stopped, which is exactly what should happen.
