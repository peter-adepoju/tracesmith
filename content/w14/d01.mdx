You are not going to become a penetration tester this week. You are going to learn **five questions** that an ordinary tester can ask of an ordinary product, without special tools, that between them find most of what is seriously wrong.

<Video id="owasp-top-10" />

## The five

1. **Can a low role do a high action?** — today
2. **Can one customer see another's data?** — tomorrow
3. **Is there anything in the response that should not be there?** — day 3
4. **Is every door actually locked?** — day 4
5. **Does the server validate what the browser refused?** — day 5

Broken access control is number one on the OWASP list, and questions 1, 2 and 4 are all forms of it. That is not a coincidence: it is the most common serious defect on the web, and testers are unusually well placed to find it.

<Callout kind="watch">
**Test only what you are authorised to test.**

Your employer's staging environment, with an account they gave you, inside your job: fine, and expected. Someone else's product, or production without a written agreement, is not a test — it is unauthorised access, and in Nigeria it falls under the Cybercrimes Act.

When you do find something, **stop at proof**. One request that demonstrates it. Do not enumerate every record to see how far it goes; you have already established the finding, and going further turns a good report into a problem.
</Callout>

## Authentication is not authorisation

The distinction the whole week rests on:

- **Authentication** — *who are you?* Signing in.
- **Authorisation** — *what are you allowed to do?* Checked per action.

<Video id="authn-vs-authz" />

The classic failure is a server that checks the first and forgets the second. You are signed in, so the request is honoured — and nobody asked whether *this* user may do *this* thing to *this* record.

It happens because authentication is one piece of shared middleware written once, while authorisation is a decision that must be made again in every single handler. One of those is easy to forget.

## RBAC

**Role-based access control**: permissions attach to roles, people get roles.

A shop might have: guest, customer, support, admin. Support can read any order and issue a refund; it cannot change prices or export the customer list.

The tester's artefact is a **matrix** — every action down one side, every role across the top, and a yes or no in each cell.

<AccessMatrix />

Fill it in from the rules first, then reveal what the server does. Six actions, four roles, twenty-four cells, and three of them are wrong.

## How to run the test

1. Get **one account per role**. Ask for them on day one of any job; this is the single most useful thing you can have.
2. Sign in as the **lowest** role.
3. Send the **highest** actions directly, by API — because the interface will not offer you the buttons, and their absence proves nothing.
4. Expect **403 Forbidden**. Anything in the 2xx range is a finding.

<Callout kind="key">
**Hiding a button is not access control.**

Removing the Delete button for customers changes what is easy, not what is possible. The request still exists, the endpoint still answers, and DevTools is free.

So the test can never be run through the interface. It has to be run against the endpoint, which is exactly why this week follows the API week.
</Callout>

## Both directions

The matrix catches the quiet failure too: a role that *should* be able to do something and cannot. That is not a security hole, it is a broken feature — and nobody reports it, because the person affected assumes they are not supposed to have it.

Same test, same grid, and you get it for free.
