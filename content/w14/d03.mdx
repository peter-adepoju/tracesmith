The page shows a name and a city. The response that fed it carried a password hash, a card number and a staff note about the customer.

This finding costs nothing to look for. Open the Network panel, click the response, and read it.

## The skill is noticing

<ExposureScan />

Fourteen lines of ordinary-looking JSON. Mark every one that should not be in a response going to the customer's own browser, then check.

Notice what the over-marking costs you. `cardLast4` and the customer's own email are fine, and reporting them alongside the five real findings makes a reader discount all of it.

## What must never reach a browser

**Credentials and secrets** — password hashes, API keys, tokens for other services, webhook signing secrets, anything named `secret` or `key`.

**Full payment details** — the card number, the CVV, the expiry. Last four digits and a brand are the correct way to show a card.

**Other people's data** — any field belonging to a different customer, however small.

**Internal fields** — risk scores, fraud flags, segment labels, staff notes, `isTestAccount`, the margin on a product.

**Infrastructure** — hostnames, internal IPs, file paths, database names, stack traces, framework versions.

**More than the screen needs** — the quiet one. An endpoint that returns the whole user row because it was easier than selecting columns.

<Callout kind="key">
**"The UI does not display it" is not a defence, and it is the sentence you will hear.**

The response reaches the browser. It is in the Network panel, in the page's memory, in any logging the browser does, and in the response cache. Whether a `<div>` renders it is irrelevant.

The correct fix is that the server does not send it.
</Callout>

## Where to look

- The **list** endpoint, which often returns full objects where the UI shows three fields
- **`/me`** or **`/profile`**, which tend to return the whole row
- **Error responses**, which leak stack traces and SQL
- **Search results**, which may match on fields they should not return
- **Anything you did not expect** — an endpoint the page calls that you did not know about

<JsonExplorer />

Use the path, not a description, when you report: `body.data[0].passwordHash`.

## Reporting without leaking it again

This is the awkward part. The report has to describe the problem, and the problem *is* the data.

> **`GET /api/customers/me` returns fields that must not reach a browser.** The response includes `passwordHash` (bcrypt), `cardNumber` (full PAN), `internalRiskScore`, `supportNotes` and `dbHost`. Reproduced signed in as any customer; the page renders none of them. Field names and types only below — no values are included in this report, and the capture is attached through the security channel rather than here. Critical: the hash is offline-crackable and the full card number is a PCI DSS violation independent of any breach.

The rules:

- **Field names and types, never values.** "Returns a `passwordHash`" — not the hash.
- **One example account**, and your own where possible.
- **Never paste the raw response** into a ticket, a chat or an email.
- **Say where the evidence is**, through whatever secure channel your team uses.
- **Name the consequence**, and the regulation if you know it. For a full card number, PCI DSS; for personal data in Nigeria, the NDPA.

<Callout kind="watch">
A ticket is forever. It is backed up, indexed, exported and often visible to contractors and new joiners for years.

Pasting a password hash into a bug report converts a serious defect into a permanent, searchable copy of the thing. The redaction drill from week 11 applies here at its strictest.
</Callout>
