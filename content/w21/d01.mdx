## Getting one running

The quickest way to have something in front of you:

```bash
npx n8n
```

It starts on `http://localhost:5678`. Nothing is sent anywhere; everything stays on your machine, which is the right place to learn.

The alternative is n8n Cloud, which is the same canvas with no setup. Either is fine for this week. Self-hosted is worth knowing because it is what most Nigerian teams run — a small VPS costs a few dollars a month and there is no per-execution charge.

## The canvas

**Nodes** are the boxes — a trigger, an action, a transformation.

**Connections** are the lines, and they carry **data** from one node to the next.

**A workflow** is the whole canvas, saved under a name.

**An execution** is one run of it, recorded, with the data each node produced.

That last one is what makes n8n good to learn on: you can open any past execution and see exactly what every node received and produced. Most debugging is just reading that.

## Your first workflow

Three nodes.

**1. Manual Trigger.** Add it first. Week 20 day 2: start manual, always.

**2. HTTP Request.** Method `GET`, URL:

```
https://api.github.com/repos/n8n-io/n8n
```

A public endpoint, no credential, returns JSON.

**3. Edit Fields (Set).** Add two fields:

| Name | Value |
| --- | --- |
| `name` | `{{ $json.full_name }}` |
| `stars` | `{{ $json.stargazers_count }}` |

Connect them in order and press **Execute Workflow**.

Each node now shows its output. Click the HTTP Request node and read what came back — it is the same JSON you would see in the Network panel, and the same reading skill from week 5.

<Callout kind="key">
**Everything in n8n is an array of items.**

Even one result is an array of one. Each item has a `json` property holding the data:

```json
[
  { "json": { "full_name": "n8n-io/n8n", "stargazers_count": 48210 } }
]
```

`{{ $json.full_name }}` means *this item's `json.full_name`*.

And the rule that follows: **if a node receives five items, it runs five times.** One HTTP Request node fed five items makes five requests. This surprises everyone once, usually when they send five emails by accident.
</Callout>

## Reading an execution

Open **Executions** in the sidebar and click your run. For each node:

- **Input** — what it received
- **Output** — what it produced
- How long it took

When something is wrong, the question is always *which node first produced something unexpected?* Walk forward until the data stops looking right. That node is the problem, not the one that threw the error.

## Naming

Rename every node to what it does. The default names — `HTTP Request1`, `HTTP Request2` — are unreadable within a week.

| Default | Better |
| --- | --- |
| `HTTP Request` | `Fetch yesterday's payouts` |
| `Edit Fields` | `Shape payout summary` |
| `IF` | `Settled?` |

A convention for workflows themselves:

```
[area] what it does — trigger
Finance: daily settlement reconciliation — 07:00
Support: chase missing KYC documents — daily
Ops: post incident summary — webhook
```

<Callout kind="watch">
**Save, and turn it off.**

A new workflow is inactive by default and runs only when you press Execute. Leave it that way until you have watched it do the right thing several times.

Activating is the moment it starts running without you — and week 20 day 5 is entirely about what happens next if nobody is watching.
</Callout>
