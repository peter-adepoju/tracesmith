A working day. One feature, one plan, written the way you would hand it to a colleague.

## The feature

Meridian is adding **saved delivery addresses**. From the ticket:

> A signed-in customer can save up to five delivery addresses. Each has a label, a recipient name, a street address, a city, a state and a phone number. One address can be marked default and is pre-selected at checkout. Addresses can be edited and deleted. A deleted address must not disappear from orders that already used it.

That is all you get, which is realistic.

## Step 1: find the ambiguities

Before any testing, read it again and list what it does **not** say. This is the shift-left habit from day 2, and it is worth more than any test you will write today.

Questions this ticket leaves open — find them yourself before reading on:

- What happens at the sixth address? An error, or does it silently replace one?
- Can two addresses be default? What if the default is deleted?
- Which fields are required? Is a phone number optional?
- How long may a label be? What about a street address?
- Can two addresses be identical?
- What does a customer with no addresses see at checkout?
- Is the state a free-text field or a list?
- What does "must not disappear from orders" mean — a copy taken at order time, or a soft delete?

That last one is a design question hiding as a detail, and the answer changes what you test entirely. **Ask it before anyone builds it.**

## Step 2: break the feature into areas

- Creating an address
- The five-address limit
- Setting and changing the default
- Editing
- Deleting, and its effect on past orders
- Using one at checkout
- Empty state, for a new customer

## Step 3: rank them

<RiskMatrix />

The tool above uses a different feature, but run the same scoring in your notes for these seven. Ask of each: how likely is it to break, and what is the damage if it does?

Two should come out near the top. **Deleting and its effect on past orders** is the most likely to be wrong, because it is the only part involving history, and getting it wrong corrupts records that already exist. **Using one at checkout** matters because it sits on the path to money.

The empty state is low impact and worth two minutes, because it is the one everybody forgets and every new customer sees first.

## Step 4: choose the types

| Area | Types |
| --- | --- |
| Creating | Functional, boundary, awkward characters |
| The limit | Boundary: 4, 5, 6 |
| Default | Functional, plus the state question of deleting the default |
| Editing | Functional, regression on orders |
| Deleting | Functional, **integration** with order history |
| Checkout | Functional, **integration**, regression |
| Empty state | UI, usability |

And across all of it: **security** — can a customer reach someone else's addresses by changing an id? That question belongs on anything with a per-customer record, and week 14 makes it systematic.

## Step 5: write the plan

One page. Someone should be able to read it and know what you will do.

```
Saved addresses — test plan

Questions outstanding
  1. Behaviour at the 6th address  (asked, awaiting answer)
  2. What happens when the default is deleted  (asked)
  3. Is a copy taken at order time, or a soft delete?  (blocks delete testing)

Priority 1  Deleting, and past orders
            Checkout with a saved address
Priority 2  The five-address limit
            Setting and changing the default
            Creating, with awkward values
Priority 3  Editing
            Empty state
Across all  One customer cannot reach another's addresses

Not covered
  Performance with many addresses — the cap is five
  Load and concurrency — not available on staging
```

<Callout kind="key">
**"Not covered" is part of the plan, not an admission.**

A plan that implies everything was tested is dishonest, and when something escapes in an area you never touched, nobody can tell whether you missed it or deliberately left it. Writing it down protects the team and protects you.

This is the same instinct as week 5's "state the gaps" and week 9's honest sign-off. It keeps recurring because it is the difference between a report that can be trusted and one that cannot.
</Callout>
