Test data is the fake-but-realistic information you test with. It sounds like a detail. It decides whether your testing means anything.

## Why it matters more than it sounds

A feature tested with `Test Test`, `a@b.com` and quantity `1` has been tested against the easiest possible case. Real data is longer, stranger and more varied, and that is exactly where the defects are.

The pattern repeats constantly: it worked in testing because the test data was tidy.

| Tidy test data | What real data does |
| --- | --- |
| `Test User` | `Adébáyọ̀ Oyelaran-Oyeyinka` |
| `a@b.com` | `peter.o.adepoju+receipts@gmail.com` |
| Quantity 1 | Quantity 0, 97, −1 |
| ₦1,000 | ₦0.50, ₦9,999,999.99 |
| One order | None, or four thousand |
| English | Yoruba, Arabic, emoji |

## The rule

<Callout kind="watch">
**Never test with real customer data.**

Not a copy of the production database, not one real customer's details "just to check", not a real card. Two reasons, and either is sufficient:

- It is a privacy breach. That data was given for a purpose, and testing is not it.
- You will eventually change something real. A test refund against a real order is a real refund.

If your team copies production data into staging, that is worth raising. The usual answer is **anonymisation** — same shape, same volume, invented values.
</Callout>

## What good test data looks like

Realistic enough to be a meaningful test, invented enough to be safe.

**Names.** Include an apostrophe, an accent, a hyphen, a very long one, and one with a single character. `O'Brien`, `Adébáyọ̀`, `Smith-Jones`, a 60-character name, `Li`.

**Emails.** A plus sign, a subdomain, a long local part, an unusually long TLD.

**Amounts.** Zero, the smallest unit, a round number, one with awkward decimals, the maximum, one above it.

**Dates.** Today, the far past, the far future, 29 February, a daylight-saving boundary, the end of a month.

**Text fields.** Empty, one character, the maximum, one over, 10,000 characters, with newlines, with emoji, with HTML like `<b>bold</b>`.

<Callout kind="job">
Build a personal set of awkward values and reuse it everywhere. A name with an apostrophe, a 10,000-character paragraph, an emoji string, a date of 29 February 2024.

It takes an afternoon once and finds defects for years. And when someone asks why you tested with `Ṣọlá O'Brien-Adébáyọ̀`, the answer is that one of your customers is called something like it.
</Callout>

## Where test data comes from

**Invented by hand.** Best for specific cases. Slow for volume.

**Generated.** Libraries like Faker produce plausible names and addresses at scale. Good for volume, and worth checking it generates awkward values and not just tidy ones.

**Anonymised production data.** Real shape and volume, values replaced. The best of both, and it must be done properly — a dataset where names are scrambled but email addresses are not is still a breach.

**Fixtures.** A known set committed alongside the tests, so everyone tests against the same thing. Essential once automation starts.

## Resetting between runs

Test data goes stale. The order you created yesterday is still there, the discount code you used is spent, the email address you signed up with is taken.

Three approaches:

- **Unique values per run.** Append a timestamp: `peter+20261107@example.com`. Simple and effective.
- **Clean up afterwards.** Delete what you created. Reliable until a test fails halfway.
- **Reset the environment.** A clean database before each run. Cleanest, and usually someone else's job.

You met this in week 8: a collection that passes once and fails the second time is usually a data problem, not a code one — and telling those apart is the skill.
